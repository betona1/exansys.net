# ADR-0003. 한국어 전문검색: FTS5 + 앱 레벨 bigram

- 상태: 채택 (2026-08-01) / v0.1(APSW+커스텀 토크나이저) 안 대체

## 배경
SQLite FTS5 기본 토크나이저 `unicode61` 은 공백 기준이라 한국어에서 무용지물이다.
조사 때문에 "머신러닝을"과 "머신러닝이"가 별개 토큰이 되어 **"머신러닝" 검색이 실패**한다.

`trigram` 은 부분문자열 매칭이 되지만 **3글자 미만 검색어를 인덱싱하지 못한다.**
한국어에서 2글자 검색어("인공", "학습", "경제")는 매우 흔하므로 치명적이다.

파이썬이었다면 APSW 로 커스텀 FTS5 토크나이저를 등록하면 됐지만,
**Dart 에서는 FTS5 커스텀 토크나이저 등록이 현실적이지 않다.**

## 결정
**토크나이저를 건드리지 않고 앱 레벨에서 해결한다.**

1. **FTS5 가 포함된 SQLite 를 번들**한다
   (OS 기본 SQLite 는 플랫폼별로 FTS5 활성화 여부가 다르다)

   > **2026-08-01 갱신**: `sqlite3_flutter_libs` 는 **폐기됐다.** 0.6.0+eol 은 코드가 비어 있고,
   > "`sqlite3` 3.x 부터는 필요 없다"고 안내한다. `sqlite3` 3.5.0 이 hooks 로 SQLite 를 직접
   > 번들하며, 기본 컴파일 플래그에 `SQLITE_ENABLE_FTS5` 가 들어 있다
   > (`lib/src/hook/compile/description.dart` 의 `_defaultDefines` 확인).
   > 따라서 **`sqlite3` 만 의존하면 되고, `sqlite3_flutter_libs` 는 넣지 않는다.**
   > 이 결정의 요구사항(FTS5 번들)은 그대로 충족된다.
2. 인덱싱 전 정규화 파이프라인
   - NFC 정규화 — NFD 자모분리 해소. **없으면 검색이 아예 안 된다**
   - NFKC — 라틴 리가처(fi/fl) 정규화
   - 제어문자·하이픈 개행 정리
   - **공백 제거 사본** 병행 저장 (한글 PDF 는 어절 공백이 실제 space 가 아닌 경우가 흔하다)
3. **bigram 그림자 텍스트 생성** — "머신러닝" → `머신 신러 러닝` 처럼 2글자씩 겹쳐 쪼개
   공백으로 이어 붙인 필드를 만들고, 그 필드를 `unicode61` FTS5 에 넣는다
4. 질의도 동일하게 bigram 변환 후 `MATCH`. 1글자 질의는 `LIKE` 폴백
5. 라틴 문자·숫자 구간은 bigram 으로 쪼개지 않고 그대로 둔다 (영어 검색 품질 유지)

## 왜 이게 맞는가
- 플랫폼·언어 의존이 전혀 없다. Android/iOS/Windows/macOS/Linux 에서 동일하게 동작한다
- 커스텀 토크나이저 네이티브 빌드가 필요 없다 (배포 복잡도 0)
- 2글자 검색어가 정상 동작한다
- `bm25()` 랭킹, `snippet()` / `highlight()` 를 그대로 쓸 수 있다

## 대가
- 인덱스 크기가 원문의 **3~5배**로 팽창한다 → 라이브러리 규모별 실측 후 캐시 정책 결정
- 정밀도가 형태소 분석보다 낮아 오탐이 늘어난다 → `bm25()` 랭킹과 스니펫으로 완화
- **성능 예산을 반드시 실측한다**: 1,000페이지 문서 최초 인덱싱 시간, 인덱스 크기, 첫 결과 지연

## 구조
`lib/core/korean.dart` 에 정규화·bigram 을 두고, 검색 계층은 인터페이스로 추상화해
나중에 서버 사이드 형태소 분석(Kiwi)으로 교체할 수 있게 남긴다.
서버에는 파이썬이 있으므로 **kiwipiepy 를 서버에서 돌려 고품질 인덱스를 만드는 경로**도 열려 있다.
