# BookViewer (북뷰) 제품 명세 v0.2 — Flutter

작성 2026-08-01 / 근거: 2025~2026 PDF 리더·전자책 뷰어 시장 리서치 + 기술 검증

## 0. 포지션

시장 조사에서 확인된 **비어 있는 자리**:

1. **"책 읽기용" PDF 앱이 거의 없다.** 대부분 "문서 뷰어"다.
   두 페이지 펼침 / 여백 크롭 / 독서 진행률 / 책장 UI 를 다 갖춘 앱이 사실상 부재
2. **읽기 + 주석 + 노트 + 라이브러리 전체 검색**을 한 앱에서 하는 제품이 없다
3. **한국어를 제대로 처리하는 PDF 앱이 없다** — 순수 차별화 영역
4. 영상→노트 도구는 전부 클라우드 구독제이고 **"내보내기가 제한적"** 이 1순위 불만
   → 우리는 **완전한 PDF 산출물 + 영구 소유**

## 1. 확정 결정

## 2. v1 기능

### 2.1 읽기 [필수]
- 한 페이지 / 연속 스크롤 / **두 페이지 펼침(표지 단독 처리 포함)**
- 맞춤: 너비 / 페이지 / **본문(여백 무시)**
- 핀치 줌, 더블탭 줌, 90° 회전(뷰 한정)
- **자동 여백 크롭** — 저해상 렌더로 비백색 바운딩박스 산출, **홀/짝 페이지 분리 계산**,
  여유 패딩 + **수동 미세조정 UI 필수** (없으면 "페이지 번호가 잘렸다" 불만 직행)
- **다크모드** — 휘도 반전 후 이미지 영역 원본 재합성. 설정 3종: 전체반전 / 이미지보존(기본) / 이미지 어둡게
- 세피아, 몰입 모드(시스템 UI 숨김)
- **독서 진행률** + `마지막 위치`와 `가장 멀리 읽은 위치`를 **따로 저장**
  (검색·목차로 점프했다 돌아올 때 진도율이 망가지는 문제 방지)
- **문서별 설정 기억** (크롭/줌/테마) — 크롭이 있으면 사실상 필수 동반 기능
- 다단 순차 보기 (리플로우의 현실적 대안. **리플로우는 미구현** — 업계 미해결)
- 태블릿/데스크톱: 좌우 분할(같은 책 두 위치 / 다른 두 책, 스크롤 동기화)

### 2.2 검색 [최대 차별화]
- 문서 내 검색 + 하이라이트 + **결과 목록**
- **라이브러리 전체 검색**
- 스캔본 OCR 검색 (서버 요청, 자동 아님 — 배터리/데이터)
- 하이라이트/메모 전체 검색
- **한국어 처리** — NFC → NFKC → 공백제거 사본 → bigram 그림자 텍스트.
  2글자 검색어("인공","학습")가 반드시 동작해야 한다. QA 필수 항목

### 2.3 캡처·복사 [가성비 최고]
- **영역 캡처** — 화면 픽셀이 아니라 **고해상도 재렌더** (150/300/600dpi)
- 텍스트 선택 복사 / 컬럼 인식 선택
- **스마트 복사** — 줄바꿈·하이픈 정리. **한글은 공백 없이, 영문은 공백으로 결합**
- 인용 복사 (본문 + 책제목 + 페이지)
- 표 → CSV/Markdown (서버 처리)
- 선택 영역 OCR (서버)

### 2.4 주석 [필수]
- 5색 하이라이트, 밑줄, 취소선, 메모
- 북마크, 목차 패널(검색 가능), 썸네일, 주석 목록(색/태그/페이지 필터)
- **앵커 = 좌표 + 원문 + 전후 문맥 + 문서 checksum.**
  파일이 바뀌면 원문·문맥으로 **자동 퍼지 재부착**, 실패분만 "위치를 잃은 주석"으로 상단 경고
- **원본에 이미 들어있는 주석**은 회색 계열로 구분 표시하고 편집하지 않는다
- 내보내기 3종
  - Markdown/Obsidian — `bookviewer://` **딥링크 필수**(없으면 죽은 텍스트)
  - **표준 PDF 주석** (pikepdf/서버) — 타 앱에서 **재편집 가능**
  - 굽기(flatten) — 보기 전용 공유
  - JSON/CSV

### 2.5 서재 [필수]
- 표지 그리드(없으면 1페이지 자동 렌더), **제목과 파일명을 함께 표시**
- 읽는중/완독/최근, 메타데이터 수동 편집(자동 메타데이터는 늘 부정확)
- 컬렉션/태그, 독서 통계(담백하게 — 뱃지·스트릭 없음)

### 2.6 부가 [v1 포함]
- **TTS 읽어주기** — `flutter_tts` + OS 한국어 음성, 읽는 구간 하이라이트. 추가 용량 0
- **번역** — 선택 영역 → 사이드/바텀 시트. 서버 Ollama. 인라인 오버레이는 레이아웃 파괴로 미채택

## 3. v2 — 영상 → 나만의 북 (전부 서버)

```
[앱] URL 입력 또는 로컬 영상 업로드 → 작업 등록
                    ↓
[Django 워커] 상태머신 + 단계별 체크포인트 (중단 시 그 단계부터 재개)
 QUEUED → FETCHING → TRANSCRIBING → SLIDES → OCR → COMPOSING → DONE/FAILED

 FETCHING      yt-dlp --write-info-json --write-subs --write-auto-subs --sub-format json3
                 ├ chapters[]        목차 1순위 (있으면 무조건 사용, 품질 최고, 비용 0)
                 ├ description 목차  2순위 정규식 파싱
                 └ json3 자막        단어 단위 타임스탬프
                    (VTT 자동자막은 중복 rolling 이라 후처리가 지저분하다)
 TRANSCRIBING  자막 없거나 품질 불량 시 faster-whisper large-v3
                 initial_prompt 에 제목+설명+챕터 주입 → 고유명사 인식률 상승 (공짜 이득)
 SLIDES        ffmpeg 1fps 저해상 → PySceneDetect → pHash 중복제거
                 톡킹헤드 배제: **정적 지속시간 3초+** 가 가장 신뢰도 높은 단일 지표
 OCR           PaddleOCR korean (슬라이드 텍스트 → 검색 인덱스)
 COMPOSING     Jinja2 → HTML → WeasyPrint(BSD) → PDF
                 Pretendard(OFL) + `word-break: keep-all` (없으면 한글이 글자단위로 끊긴다)
                 문단마다 <a href="youtu.be/ID?t=sec"> → PDF Link 주석 자동 생성
                 + sync.json (segment ↔ 초 ↔ page/rect)
                    ↓
[앱] 완성 PDF + sync.json 수신 → 서재에 등록 → 읽으면서 문단 탭하면 영상 그 지점 재생
```

**개발 순서는 로컬 영상 파일이 먼저다.** 법적 리스크 0 으로 파이프라인 전체를 검증할 수 있고,
yt-dlp 는 그 위에 얹는 입력 어댑터 하나일 뿐이다.

**법적 방어**: 생성물 개인 학습용 명시, 원본 URL·채널·타임코드 항상 포함(대체가 아닌 보완),
공유 기능 미제공, 원본 미디어 파일 처리 후 자동 삭제, **ffmpeg 는 LGPL 빌드만 사용**.

## 5. 성능 원칙
- 페이지 렌더는 pdfrx 에 맡기되 **썸네일·인덱싱은 Isolate** 로 뺀다
- 스크롤 중 저해상 → 정지 후 풀 해상도 교체
- 텍스트+bbox 는 최초 1회 추출 후 DB 저장. 매번 추출하지 않는다
- 썸네일은 WebP 로 디스크 캐시
- 300MB PDF·1000페이지에서 메모리 상한을 실측해 캐시 예산을 정한다

## 7. 수익 모델 (2026-08-01 결정)

**앱은 북뷰 하나다.** 앱을 쪼개 팔지 않는다.

```
북뷰 앱 하나
 ├─ Free            기본 무료
 ├─ Pro 영구 이용권  1회 구매 · 영구 (구독 아님)
 └─ 크레딧          소모형 — 서버가 일한 만큼
```

### 왜 이 구조인가

- **구독이 아니라 영구 이용권.** 조사에서 확인된 1순위 불만이 "구독제 + 내보내기 제한"이었다.
  거기에 구독으로 답하면 우리가 지적한 문제를 그대로 반복하게 된다
- **크레딧은 서버 비용이 실제로 발생하는 것에만 쓴다.** 영상→북 변환, 대량 OCR, 번역처럼
  GPU·시간을 태우는 작업이다. 앱 안에서 끝나는 일에는 크레딧을 물리지 않는다
- 따라서 Pro 를 사도 서버 작업에는 크레딧이 필요할 수 있다. 이 경계를 UI 에서 흐리지 않는다

### 절대 규칙

1. **PDF 읽기·검색·복사·캡처·주석은 영구 무료다.** 페이지 수나 권수로 잠그지 않는다
2. **서버가 죽어도, 크레딧이 0 이어도 읽기는 100% 동작한다.** 이건 이미 설계 제약이다
3. 무료 기능 버튼을 유료처럼 보이게 만들지 않는다
4. 크레딧 차감은 **작업 성공 완료 기준**. 취소·실패는 복구한다
5. 잠긴 기능은 숨기지 않고 자물쇠 + 이점 한 줄. 사라지면 기능이 없다고 오해한다

### 1차 출시는 Free 만 (2026-08-01 결정)

**결제·크레딧을 만들지 않고 Free 로 먼저 낸다. 목표는 다운로드 500~1000.**

- 유료 코드(결제·라이선스 검증·크레딧 차감)를 **지금 넣지 않는다.** 쓰지도 않을 결제 SDK 와
  권한 분기가 코드 전체에 퍼지면 되돌리는 비용이 크다
- 대신 되돌리기 쉽게 남겨 둘 것: 서버가 하는 무거운 작업(영상→북·OCR·번역)은
  처음부터 **작업(job) 단위**로 만든다. 나중에 크레딧을 붙일 지점이 그 경계 하나로 모인다
- 이 단계에서 봐야 할 숫자는 매출이 아니라 **다운로드 수와 재방문**이다.
  읽기 자체가 좋아서 매일 열리는지가 유료화 이전에 증명되어야 한다
- 목표에 닿으면 그때 위의 Pro·크레딧을 얹는다

### 아직 정하지 않은 것

- Free 와 Pro 의 정확한 경계 (두 페이지 펼침·여백 크롭·내보내기 3종을 어디에 둘 것인가)
- 크레딧 단가와 작업별 소모량 — 서버 실측 후 정한다
- Pro 구매자에게 주는 초기 크레딧 유무
- 데스크톱 미서명 배포에서의 구매·인증 경로 (Play 결제는 Android 한정)

> ⚠ `CLAUDE.md` §1 의 "배포: 무료 · 고정비 0" 은 **배포 인프라 비용**을 뜻한다.
> 유료 티어가 생기면 결제·라이선스 검증 경로가 필요하므로 고정비 0 은 더 이상 성립하지 않는다.
> 결제 수단을 정할 때 이 항목을 함께 갱신한다.
