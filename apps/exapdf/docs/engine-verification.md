# pdfrx 엔진 검증 결과 (2026-08-01)

ADR-0001 이 pdfrx 를 채택한 근거는 문서 조사였다. 이 문서는 **실제로 코드를 돌려
확인한 결과**다. 검증 앱은 `app/lib/main.dart` 의 초기 버전이었고, 표본은
`data/sample_book.pdf` (4쪽, 한글+영문, 쪽마다 표식 문자열).

환경: pdfrx 2.4.7 / Windows 릴리스 빌드.

## 결과 — 8개 항목 전부 통과

| 검증 항목 | 결과 |
|---|---|
| 전체 쪽 로드 | 4쪽 · 5ms |
| 텍스트 추출 (한글+영문 혼합) | 1쪽 177자, 한글 O · 영문 O |
| 쪽 단위 정확도 | 4개 쪽의 표식이 모두 제자리 |
| 검색 — 한 곳에만 있는 낱말 | `[3]` (기대 `[3]`) |
| 검색 — 여러 쪽에 걸친 한글 낱말 | "검색" → `[1, 2, 4]` |
| 검색 — 없는 낱말 | 오탐 없음 |
| 문서 열기 · 쪽 수 | 4쪽 |
| 색인 경로 (뷰어 없이 전체 추출) | 4쪽 · 580자 · **1ms** |

## 반드시 기억할 것 — 점진 로드 함정

pdfrx 는 **점진 로드(progressive loading)** 를 쓴다. `PdfViewer` 가 뷰어를 띄운 시점
(`onViewerReady`)에는 **1쪽만 실제로 열려 있고 나머지 쪽은 껍데기**라
`page.loadText()` 가 조용히 **빈 문자열**을 준다. 예외도 나지 않는다.

첫 검증에서 2·3·4쪽이 전부 빈 값으로 나와 6개 중 3개가 실패했던 원인이 이것이다
(표본 PDF 자체는 pypdf 로 확인했을 때 4쪽 모두 정상이었다).

따라서 **검색 색인을 만들 때는 반드시 둘 중 하나를 한다**:

```dart
// 1) 뷰어의 문서를 쓸 때 — 모든 쪽을 명시적으로 로드한 뒤 추출
await doc.loadPagesProgressively();

// 2) 뷰어와 별개로 색인만 만들 때 (권장 — 실제 구현 경로)
final doc = await PdfDocument.openAsset(path, useProgressiveLoading: false);
```

SPEC §2.2 의 라이브러리 전체 검색과 ADR-0003 의 bigram 인덱싱은 (2) 경로를 쓴다.

## 또 하나 — PdfTextSearcher 는 문서가 열린 뒤에만 만들 수 있다

`PdfTextSearcher(controller)` 는 생성자 안에서 곧바로 `controller!.document` 를
참조한다. 뷰어가 준비되기 전에 만들면 읽기 화면이 통째로 죽는다
(`Null check operator used on a null value`). `onViewerReady` 에서 만든다.

## 색인 성능 실측 (2026-08-01) — ADR-0003 요구 항목

도구: `app/lib/benchmark_main.dart`

```
flutter run -t lib/benchmark_main.dart -d windows --release --dart-define=pdf="<경로>"
```

측정 대상 PDF 는 **저장소에 넣지 않는다** (CLAUDE.md §9 — 저작권 있는 책 금지).
경로만 받아 그 자리에서 읽고, 만든 DB 는 임시 폴더에 두었다가 지운다.

### 표본 A — 한글 텍스트 500쪽 (합성, 0.62MB, 41.5만자)

| 항목 | 개선 전 | **개선 후** |
|---|---|---|
| 문서 열기 | 44ms | 43ms |
| 색인 전체 | 5,609ms | **564ms** (쪽당 1.1ms) |
| ├ 텍스트 추출 | 277ms | 225ms |
| ├ 정규화 | 166ms | 157ms |
| ├ bigram | 17ms | 16ms |
| └ **DB 적재** | **5,144ms (92%)** | **162ms** |
| 인덱스 크기 | 4.89MB | 4.89MB |
| 질의 (2글자, 200건) | 1ms | 1ms |

**병목은 한국어 처리가 아니라 DB 적재였다.** 쪽마다 INSERT 를 따로 커밋해서
500쪽 색인 5.6초 중 5.1초가 거기서 났다 — 추출·정규화·bigram 을 다 합친 것(460ms)보다
열 배 넘게 컸다. 50쪽씩 배치로 묶어 **10배** 빨라졌다.

측정하지 않았으면 한국어 처리를 붙잡고 최적화했을 것이다. 재고 나서 고칠 것.

- bigram 팽창률 **1.38배** (41.5만자 → 57만자). ADR-0003 이 걱정한 "3~5배"보다 작다.
  다만 인덱스 크기는 원문 대비 **12바이트/자** 수준이라 별개로 봐야 한다
- 질의는 200건을 뽑아도 1ms 이하. bm25 랭킹 포함

### 표본 B — 실제 스캔본 102쪽 (14.8MB)

`etc/나를잃어가면서지켜야할관계는없다.pdf`

| 항목 | 결과 |
|---|---|
| 문서 열기 | 13ms |
| 텍스트가 있는 쪽 | **0 / 102** |
| 색인 | 0자 — 색인할 것이 없다 |

**순수 스캔본이다.** pypdf 로 따로 확인했을 때도 102쪽 전부 0자였고,
쪽마다 이미지 XObject 가 정확히 1개씩 있었다. 내 코드 문제가 아니다.

또 하나 확인된 것: 쪽 크기가 **1331 × 717** 로 가로가 더 길다.
**책을 펼친 채 스캔해 한 장에 두 쪽이 들어 있다.** 폰에서 그대로 보면 글자가
절반 크기가 되어 읽을 수 없다 → 좌우 나눠 보기 기능의 근거가 되었다 (techspec §6.2-1).

### 남은 측정

- **300MB·1000쪽 이상** 문서에서의 메모리 상한 (SPEC §5 가 요구)
- Android 실기기에서의 색인 시간 — 데스크톱보다 느릴 것이 확실하다
- 색인이 메인 아이솔레이트에서 도는 문제. 500쪽 564ms 면 체감되지 않지만,
  느린 기기의 큰 문서에서 어떤지 재고 나서 Isolate 이전을 결정한다

## OCR 실측 — Ollama 비전 모델 (2026-08-02)

스캔본에서 검색이 안 되는 문제의 해법을 실제로 돌려 확인했다.
**만들기 전에 재 본다** — pdfrx 때와 같은 순서다.

### 표본

`etc/나를잃어가면서지켜야할관계는없다.pdf` 102쪽.
`pypdf` 로 여러 쪽을 뽑아 보니 **글자가 한 자도 나오지 않는다 — 완전 스캔본이다.**
(위 검증에서 "표본이 없다"고 적었던 항목이 이 파일로 채워졌다.)
쪽마다 좌우 두 쪽이 한 장에 들어 있어, 앱의 분할 규칙대로 **반쪽씩** 넣었다.

### 서버

`192.168.219.88:11434` Ollama. `qwen2.5vl:7b`(4.7GB, VRAM 전량 적재) ·
`qwen2.5vl:3b` · `exaone3.5:7.8b`(한국어 텍스트 전용).

### 품질 — 사실상 완벽

150dpi 반쪽(1386×1493)을 `qwen2.5vl:7b` 에 넣어 나온 1,164자를 원본 그림과
한 줄씩 대조했다. **틀린 글자가 없다.** 작은따옴표·큰따옴표, 쉼표, 쪽 끝에서
잘린 말("그 다름 때문에 불")까지 그대로다. 한국어 OCR 을 LLM 으로 하는 것에
품질 의문은 없었다.

### 속도 — 여기가 문제다

| 구간 | 값 |
|---|---|
| 그림 읽기(prompt eval) | **75.9초** · 2,682토큰 |
| 글자 생성(eval) | 4.3초 · 526토큰 · **121 tok/s** |
| 모델 적재 | 5.4초 (처음 한 번) |

생성은 빠르다. **시간의 88%가 그림을 토큰으로 바꾸는 데 들어간다.**
따라서 줄일 곳은 모델이 아니라 **해상도**다.

### 해상도를 낮춰도 글자는 그대로다

같은 반쪽을 폭만 줄여 넣고, 1386px 결과와 글자 단위로 대조했다.

| 폭 | 걸린 시간 | 그림 토큰 | 1386px 대비 일치율 |
|---|---|---|---|
| 1386px | 87.3초 | 2,682 | (기준) |
| 1100px | 49.4초 | 1,670 | **100%** |
| 900px | 33.7초 | 1,152 | **100%** |
| 700px | 32.4초 | 1,086 | **100%** |

**900px 에서 2.6배 빨라지고 글자는 한 자도 달라지지 않는다.**
700px 부터는 더 줄여도 이득이 없다 — 모델의 타일 격자 때문에 토큰 수가
더 내려가지 않는다. **보낼 때 폭 900px 로 줄인다**가 결론이다.

### 그래서 책 한 권은

반쪽당 약 33초. 이 책(102장 × 2쪽)이면 **약 1시간 50분**.
사람이 앞에서 기다릴 수 있는 시간이 아니다. 그러므로 OCR 은
**서버가 뒤에서 도는 작업**이어야 하고, CLAUDE.md §2 규칙 7 대로
쪽 단위 체크포인트를 남겨 **중간에 죽어도 이어서** 돌아야 한다.
끝나면 앱이 받아 `page_texts` 에 넣고 색인한다.

더 빠르게 하려면 전용 OCR(PaddleOCR 등)이 필요하다 — 쪽당 1~2초 수준이라
두 자릿수 배 차이다. 다만 서버에 따로 설치해야 하고(SSH 필요), 비전 LLM 은
**이미 올라와 있어 오늘 바로 쓸 수 있다.** 먼저 붙이고, 느려서 못 견디면
그때 바꾼다.

### 함정

- **펼침 그대로 넣으면 안 된다.** 2773×1493 한 장을 통째로 넣었더니 34자만
  내놓고 멈췄다. 반쪽으로 자르니 정상으로 끝까지 나왔다
- `num_predict` 를 올리지 않으면 기본값에서 잘린다 (`done_reason: length`).
  반쪽 한 장에 2,500 이면 넉넉하다
- `qwen2.5vl:3b` 는 7b 보다 **느렸다**(117초). 작다고 빠르지 않다 —
  병목이 그림 인코딩이라 파라미터 수와 무관하다

## 아직 확인하지 않은 것

- **여러 책·다른 판형에서의 OCR 정확도** — 위 실측은 한 권 한 쪽이다.
  가로쓰기 본문에서 완벽했을 뿐, 표·수식·2단 논문은 재지 않았다
- **기울어지거나 그림자 진 스캔** — 이 표본은 반듯하다
- **큰 문서(300쪽+·300MB) 색인 시간·메모리** — 4쪽 580자가 1ms 였으나 규모 검증은 별개다.
  ADR-0003 이 요구하는 성능 실측(최초 인덱싱 시간·인덱스 크기·첫 결과 지연)은 아직이다
- **Android 실기기** — Windows 데스크톱에서만 확인했다
- **주석 렌더·암호 PDF·목차** — 이번 검증 범위 밖
